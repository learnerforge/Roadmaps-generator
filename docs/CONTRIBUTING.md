# Contributing to PathForge AI

## Code of Conduct

This project follows a standard Code of Conduct. By participating, you agree to maintain a respectful, inclusive environment. Report unacceptable behavior to the maintainers.

## Before You Start

Checklist for your first contribution:

- [ ] Python 3.11+, Node.js 20+, and PostgreSQL 16+ are installed (or Docker 24+ if you use the Docker setup).
- [ ] You can run the app locally using the setup steps below.
- [ ] `.env` exists (copy from `.env.example`) with `DATABASE_URL` and `JWT_SECRET` set.
- [ ] The `pathforge` database has been created and seeded (`createdb pathforge`, then the seed steps below).
- [ ] AI API keys are configured only if you need AI features — `GEMINI_API_KEY` and/or `OPENAI_API_KEY` are optional. Without them the app runs but AI explanations, quizzes, projects, and weekly plans will not work.
- [ ] Linting works: `ruff check app/` (backend) and `npm run lint` (frontend).

### Backend

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # macOS / Linux
cd backend

pip install -r requirements.txt

copy .env.example .env        # Windows
cp .env.example .env          # macOS / Linux
# Edit .env — set DATABASE_URL, JWT_SECRET, and at least one AI key

createdb pathforge

# Fetch content bodies (cached in content_body_cache.json) and seed roadmaps
python fetch_content.py
python -m seed_data

# Start dev server
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

```bash
cd frontend

```

## Contributing Content / Roadmap Data

Roadmap data is seeded from the roadmap.sh GitHub repository by `backend/seed_data.py`. Topic descriptions come from the content body cache generated by `backend/fetch_content.py`. To refresh roadmap content, run these from `backend/`:

```bash
python fetch_content.py        # download content bodies into content_body_cache.json
python -m seed_data            # idempotent — existing roadmaps are skipped, safe to re-run
```

Run `python fetch_content.py --force` to re-fetch everything, and `--stats` to inspect cache coverage. The seed script is idempotent, so re-running it is safe.

## Code Style Guidelines

### Python (Backend)

- **Formatting**: Follow PEP 8. `ruff` is the project linter/formatter convention (see Running Linting). Note: ruff is not pinned in `requirements.txt` — install it separately with `pip install ruff`.
- **Imports**: Group in order: standard library, third-party, local. Use absolute imports.
- **Types**: Use type hints for all function signatures and public methods.
- **Async**: All database operations use `async/await` with SQLAlchemy async sessions.
- **Pydantic**: Use Pydantic v2 models for request/response schemas. Use `model_dump()` and `model_validate()`.
- **Routes**: Keep route handlers thin — delegate business logic to `app/services/`.
- **Error handling**: Raise `HTTPException` with descriptive `detail` messages. Do not leak stack traces.

### JavaScript / JSX (Frontend)

- **Formatting**: Use Prettier with the project's `frontend/.prettierrc` config. Run `npm run format` (writes changes).
- **Linting**: ESLint (config in `frontend/.eslintrc.cjs`) with `eslint-plugin-react` and `eslint-plugin-react-hooks`. Run `npm run lint` before committing; the script treats warnings as errors.
- **State management**: Use Zustand stores for global state (auth, user prefs). Use React state/hooks for local UI state.
- **Components**: Prefer function components with hooks. Use named exports, not default exports.
- **CSS**: Use Tailwind CSS utility classes. Avoid inline styles and custom CSS files unless necessary.
- **API calls**: Use the shared API client in `src/lib/api.js`. Never call `fetch` directly in components.

## Running Linting

### Backend

```bash
cd backend
pip install ruff            # ruff is not in requirements.txt
ruff check app/
ruff format --check app/
```

### Frontend

```bash
cd frontend
npm run lint                # eslint with --max-warnings 0
npm run format              # prettier --write over src/**
```

## Testing

Automated tests are not set up yet. There is no `backend/tests/` directory and pytest is not in `backend/requirements.txt`; the frontend has no test runner (no Vitest dependency and no `test` script in `package.json`). Test coverage — including end-to-end tests for auth, progress tracking, AI features, and admin flows — is planned; see the **Future Work** section of the [README](../README.md#future-work).

Until tests land, verify changes manually: start both dev servers, exercise the affected endpoints (Swagger UI at `http://localhost:8000/docs`) and pages, and re-run the linters above.

## PR Workflow

1. Fork the repository.
2. Create a feature branch from `main`:
   ```bash
   git checkout -b feat/your-feature-name
   ```
3. Make your changes. Keep commits small and focused.
4. Run linting and ensure no warnings:
   - Backend: `ruff check app/`
   - Frontend: `npm run lint`
5. Verify your changes manually against the running dev servers (see Testing above).
6. Commit with a descriptive message:
   ```bash
   git commit -m "feat: add brief description of the change"
   ```
7. Push to your fork and open a Pull Request against `main`.
8. In the PR description, explain:
   - What the change does
   - Why it's needed
   - How to test it
   - Screenshots for UI changes
9. Re-run linting after your final edits. There is no CI pipeline configured yet, so local verification is what reviewers rely on.
10. Request review from a maintainer.

### Commit Message Convention

Use [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` — new feature
- `fix:` — bug fix
- `docs:` — documentation only
- `refactor:` — code change that neither fixes a bug nor adds a feature
- `test:` — adding or updating tests
- `chore:` — build process, CI, tooling
